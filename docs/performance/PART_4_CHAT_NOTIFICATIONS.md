## Complete flow and transaction boundary

1. Flutter `OrderChatScreen._sendMessage`, **`lib/modules/chat/screens/order_chat_screen.dart:1281`**, prepares an optimistic message with a stable UUID and persists the outbox before POST. `ChatMessageDelivery._send`, **`lib/modules/chat/services/chat_message_delivery.dart:74`**, serializes per account and joins an identical pending message. `_insert:146` sends the UUID as the database primary key, with a narrow response projection. These pre-existing retry/persistence fixes are preserved.
2. PostgreSQL applies the participant INSERT policy, captured at **`chat-notifications-20261102/CATALOG.json:344`**. The BEFORE trigger [prevent_chat_before_intercity_acceptance](chat-notifications-20261102/prevent_chat_before_intercity_acceptance.production.sql), **lines 14/21**, checks agent roles and pending intercity requests. Local tests retain pre-acceptance blocking.
3. AFTER INSERT [on_new_chat_message](chat-notifications-20261102/on_new_chat_message.production.sql), **lines 16/22/28/47**, resolves sender display name, order customer and rider user, then calls `send_push_notification_fnc`. No recipient means no notification. An initial customer support message with no agent recipient does not broadcast to support staff; staff inbox discovery is a separate flow.
4. [send_push_notification_fnc](chat-notifications-20261102/send_push_notification_fnc.production.sql), **line 31**, INSERTs `notifications` **inside the Chat transaction**. Its ordinary exception handler at **line 48** records a best-effort failure. The notification AFTER trigger [on_notification_insert](chat-notifications-20261102/on_notification_insert.production.sql), **line 10**, calls the delivery helper with the notification ID.
5. [deliver_push_notification_http_fnc](chat-notifications-20261102/deliver_push_notification_http_fnc.production.sql), **lines 21/44**, looks up the service key and invokes `net.http_post(timeout_milliseconds := 5000)`. Enqueue is synchronous SQL work; outbound HTTP delivery is asynchronous. The 5 s setting is a downstream request timeout, not a five-second wait in every Chat INSERT. The trigger does not inspect the eventual HTTP response or retry it.
6. Edge `send-push-notification` authenticates, checks recipient scope, feature flag/preferences, reads device registrations, signs/caches OAuth credentials, sends FCM HTTP v1 requests with the existing 10 s fetch deadline, then updates delivery state. In-app inbox state and FCM delivery are distinct.

**Native failure reproduction:** using the five captured production PL/pgSQL bodies, captured participant policy expressions, synthetic related tables and a fake local `net.http_post`, an actual PostgreSQL `statement_timeout` cancelled the entire message/notification/enqueue transaction. `WHEN OTHERS` does not swallow query cancellation. An ordinary injected enqueue exception instead committed the message and inbox row, left no queued delivery, and recorded `notification_failures`. Thus a normal provider rejection is not the cause of a Chat HTTP500 through this chain, while synchronous SQL cancellation can be. Production pg_net, managed Auth and actual trigger timings were not reproduced.

## Remaining issues and Part 5 handoff

1. **Incident initiating cause remains unresolved.** Missing incident CPU/RAM/swap/disk-I/O, backend wait/concurrency/lock snapshots and per-trigger/RLS timings remain as documented in Part 1. No matched request-level evidence separates base INSERT, policy reads, notification work, enqueue, pool waits and other database contention. FCM/provider latency is downstream and does not establish this initiating cause.
2. **Push exactly-once is not solved.** Two simultaneous replay requests still send twice in the new negative-capability test. FCM acceptance followed by a failed status write is also ambiguous and replayable. `push_sent=true` means at least one device succeeded, not every device received it. A durable per-notification/per-registration claim/lease, bounded retry policy and reconciliation need design and fencing; do not use a pre-send read as an atomic lock. No automatic retry worker was added.
3. **Missing notification/push recovery remains.** Captured ordinary exceptions can leave committed chat without a notification, or committed inbox without enqueue. The existing failure table is best-effort; pg_net responses are not consumed here. Need bounded queue-age/status metrics and a secure replay/reconciliation path keyed to message/notification IDs. Do not re-INSERT chat to repair push delivery. Check exact support recipient/agent notification requirements separately.
4. **Read/loading limits remain.** Chat history reads the full scoped conversation; inbox uses offset pagination and timestamp-only ordering. Native read transport cancellation and bounded error UX for never-settling history/profile/inbox requests are not implemented. Already-issued HTTP reads/POSTs are not magically cancelled by dispose; late results are guarded and the next queue POST is stopped. Notification tap still has a non-cancelling 8 s mark-read timeout (`notification_service.dart:345`) and pending-tap persistence deserves an account-switch review. No generic retry storm or safe global retry replacement was proven.
5. **Security/managed integration gates.** Test policy candidates with actual managed users, participant/agent roles, old-client support initialization and rider-recipient parity. This insert-only correction does not certify all UPDATE/DELETE or rider selection policies. Existing attachment helpers at screen **1390+** and auto order-info insertion at **285–309** do not use the full text outbox/idempotency path; attachment UI is currently unused by the analyzer. Do not claim all message types have durable offline delivery. Test encrypted-at-rest/outbox retention requirements separately; persistence remains the pre-existing SharedPreferences design.
6. **Part 3 safety handoff remains open:** cross-writer dispatch races, eligibility parity, per-order enqueue coalescing, and **resumed-owner fencing** for stale-worker recovery. Push-delivery suppression does not coalesce dispatch HTTP work or fence resumed workers. **Do not deploy the stale-worker recovery candidate** without fencing validation. No dispatch writer, trigger, cron or acceptance path was changed here.
7. Reconcile the sixteen broader source-contract failures against current prior-part implementations without weakening their intended invariants. Then run controlled managed fault/load and physical-device tests for unread reconciliation, late joins, send ordering, foreground/background push, token rotation and auth degradation. No paid environment was created for these checks.
