## Assessment

There are real client wait/retry problems, backend request amplifiers, security/concurrency gaps and a release gap between local corrections and the deployed app/backend. The available evidence does **not** support attributing all slowness to Flutter, Supabase Free plan, or one missing index.

**Release position:** reviewed Flutter subset remains conditional on device validation; coordinated dispatch/acceptance/push SQL and Edge remain **NO-GO**. Independent changes that previously shipped are not evidence that these combined bundles shipped. No new release approval is implied by this review.

This is a targeted review of startup/account, Rider Home, pricing/booking, completion/photo proof, chat/push and dispatch paths, supported by existing reproductions and selected fresh production metadata. It is not a line-by-line security audit of every screen/function, a penetration test, or a new production load test.

## Recommended execution order for a later authorized implementation

1. **Close security/integrity release blockers:** chat sender/support RLS, photo current-assignment/atomic proof, acceptance/cross-writer protocol and scoped durable push. Use an approved isolated environment and synthetic destinations, not live customer orders/payments/messages. No new project is created by this report.
2. **Select independent performance candidates:** exact captured-v54 cache-only patch and reconciled pricing zone-cache patch; avoid unrelated local handler differences. Retain tested rollback/fail-closed behavior and monitor call/error counts.
3. **Unify the rider proof transport:** address the still-direct path rather than assuming booking-uploader fixes cover every photo flow. Test uncertain response, account/disposal, idempotency and body-consumption deadline.
4. **Prepare a distinct reviewed APK** containing the latest client fixes; perform matched cold/warm launches, Home, completion→Home, booking and photo journeys on the same device/network. No arbitrary promise of 100% speed.
5. **Capture the next genuine slow interval once, narrowly:** API/Storage status and header/body duration, DB active/waiting/locks and host CPU, available RAM/swap, disk latency/IOPS/queue depth, compute size and connection/pool metrics. Compare onset rather than cumulative workload. Historical chart availability must be verified rather than assumed.
6. **Then optimize measured scoring/RLS/lifecycle work** while preserving eligibility, tracking, acceptance/payment and notification guarantees. Do not disable cron/Realtime or remove required validation/writes to make a spinner disappear.

The backend-wide November 1/2 initiating cause remains **unproven**. Current evidence supports targeted fixes and controlled rollout/measurement, not a blanket backend upgrade or whole-working-tree deployment.
