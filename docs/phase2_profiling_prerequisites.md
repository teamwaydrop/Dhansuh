# Profiling prerequisites — operator checklist

This is a preparation checklist, not permission to provision infrastructure or launch against production. Previous device discovery found desktop/browser targets only; it is not repeated here. All performance values remain unmeasured.

1. **Approved target:** owner confirms the non-production project reference, synthetic passenger/rider resources, allowed ride/parcel scenarios and request budget. Verify the reference against the operator's approved project inventory and dashboard locally. Production reference `yvwpchffctiagevpqgwy` is forbidden. URL naming alone is not authorization. No project credentials belong in chat or artifacts.
2. **Separate build:** operator provides an untracked local JSON define file outside the checkout containing the required `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `OLA_MAPS_API_KEY` keys. Confirm URL host matches the approved non-production reference, key belongs to that target and maps/payment/push integrations are approved test integrations. Do not print file contents or decode tokens into logs. Existing configuration uses compile-time defines; ordinary `.env` is not a safe default. Record only configuration-file hash, approved project reference, key-presence booleans and source revision/dirty-state summary. Inspect startup/dependent integration behavior before launch; stop if an integration could contact production.
3. **Android:** connect an authorized physical device, enable developer options/USB debugging and accept its host authorization prompt. With the operator's existing SDK path, run `& '<SDK>\platform-tools\adb.exe' devices -l`, then `flutter devices --machine`. Require state `device` (not unauthorized/offline), Android target and selected-device agreement. Device serials stay local. If SDK/tools are missing, obtain separate installation approval; do not install automatically. Use `flutter doctor -v` locally to diagnose toolchain readiness; sanitize paths/identifiers before sharing.
4. **Build/run after all checks:** `flutter run --profile --no-pub -d '<ANDROID_DEVICE_ID>' --dart-define-from-file='<LOCAL_NONPROD_DEFINES.json>'`. Do not run this until target/integration verification passes. Record profile mode, Flutter/device versions, app configuration hash and locally observed app connection to the approved host without recording authorization headers or bodies. A prior APK is insufficient evidence of target configuration.
5. **Capture access:** use the installed Flutter run command's DevTools launch option/help and local VM service connection; keep VM service URLs/tokens private. Confirm Performance and Memory captures export successfully before the scenario. Establish existing sanitized HTTP/Realtime/GPS counter access; if unavailable, stop that measurement rather than infer it from source timers. Backend metrics require independently approved non-production monitoring access.
6. **Artifacts:** choose a new operator-owned directory outside the checkout, e.g. `<LOCAL_ARTIFACT_ROOT>\waydrop-profile-<UTC_RUN_ID>`. Export to `flutter-timeline.json`, `memory.csv` (or DevTools native format), `requests.csv`, `realtime.csv`, `gps.csv`, `flow-events.csv` and `run-manifest.json`. Record actual format/path if tools differ. Request data contains endpoint categories, monotonic/UTC timestamps, status/error category and duration only; exclude URLs with IDs, payloads, tokens and precise locations. Manifest records window boundaries, device refresh rate, scenario, approved target, configuration hash and capture gaps. Validate nonempty files and inspect for sensitive content locally before any sharing.

Use the equal-duration windows and abort rules in `phase2_bounded_stability_validation.md`. Next executable step is operator target/build approval and device connection; connectivity commands above are then read-only readiness checks. App launch, synthetic flow and capture follow only after readiness passes. No load-test capacity claim follows from one device.
