## Existing indexes versus additions

- **Keep:** uq_production_config_active; users/riders primary and unique ownership keys; idx_rider_kyc_user_id; orders(user_id,created_at DESC,id DESC); orders(rider_id); searching(created_at) partial index; rider_assignments(order_id,rider_id) unique key; notifications(user_id,is_read). These already support the relevant equality/join paths.
- **Reuse, do not duplicate/drop blindly:** riders(account_status,service_mode) INCLUDE coordinates, online-coordinate and freshness indexes. Recorded scans are 402, 599 and 14,516 respectively. Adding another location index would increase GPS write amplification. No new matching index is presently proven necessary.
- **Safe-equivalent cleanup candidate:** two non-constraint duplicate rider user/kyc indexes. Both are actually used (143,830/145 scans), so replacement query plans must be checked against the retained equivalent unique keys; zero scans is not the argument for removal.
- **Only new index candidate:** ongoing/unnotified orders(rider_id) in the separate 02b file. It is optional, not an established missing-index incident; baseline estimated proximity cost is already small. No enum-to-text expression in its predicate.

Do **not** suppress proximity checks solely on unchanged coordinates: a stationary rider may have just entered ongoing status and need the arrival notification. Removing these heartbeat checks requires a separately tested order-state re-evaluation design. The current proposal preserves them, the bridge and dispatch freshness.

## First three fixes after staging approval

1. **01 matching candidate reduction**, differential-test then retain only with lower candidate work and no materialization regression. Highest P0 query-side opportunity; historical workload, not proven current load.
2. **02 lean GPS maintenance**, test duplicate-index removal first; keep the new partial index only if measured. No coordinate-write/table-contract change.
3. **03 push delivery**, validate single-flight/prefetch and use its phase logs to locate the remaining ~2.3 s. This is the strongest fresh function-latency sample.

**Ahead of claiming startup fixed:** complete the config/gateway attribution using 05 and correlated platform request traces. Current SQL evidence does not support a database-index fix for the ~685 ms origin delay. Suspected queue/cold/gateway causes remain explicitly unknown.

## Validation, staging acceptance and rollback

Local only: [six validation groups](evidence/LOCAL_VALIDATION.json) pass, including **56 actual original/proposed nearby-SQL result comparisons** over synthetic vehicles/statuses/radii; unchanged matching bodies after removing the explicit inserted optimizations; executable index/RLS rollback-default checks; ten concurrent OAuth requests sharing one mint plus failure/retry; and push gate ordering. Node TypeScript syntax check passes. Engine is **PostgreSQL 18.6/PGlite**, production is **17**; mode/busy/threshold dependencies are fixture stubs. This is neither a production benchmark nor complete dispatch/financial validation. Core assignment writes were not exercised locally.

Required before deployment:

1. On an approved PostgreSQL 17 staging clone, compare exact eligibility/result sets and limited ordering: radius zero/boundaries, NULL/negative/NaN, poles/dateline, invalid existing coordinates, rounded-distance ties, all vehicle/weight/mode/tax/COD/busy/excluded/stale cases. Preserve the existing 24-hour/null location acceptance; do not silently tighten eligibility.

3. EXPLAIN (ANALYZE,BUFFERS) representative staging matching and GPS UPDATEs, including trigger timing, stationary/moving heartbeat, heading changes, ongoing transition while stationary, destination notification exactly once and reconnect. Compare WAL/CPU/index maintenance per equal workload, not cumulative totals across resets.
4. Check anon/ordinary/other-user/admin/server access before/after 04. Assert denied rows stay denied and normal login/KYC/order/payment/payout flows still work.
5. Test push preferences/modes, disabled global flag, empty/invalid tokens, cold/warm/expired OAuth, concurrent refresh failure/retry, provider timeout, delivery-status and duplicate-event behavior. No production FCM tokens or live payments.
6. Capture matched config API/gateway/SQL timing. Stop and reject any change without a demonstrated relevant improvement; no numerical improvement is promised here.

All SQL files end in **ROLLBACK**, remain outside migrations, and contain drift checks. For a future approved deployment, capture the target definitions/ACLs/indexes first; stage the final commit/concurrent-index strategy separately. Roll back 01 to the exact saved pre-change function definitions; 02 by recreating the two captured index definitions and removing only the new index; 04 to its original is_admin() expressions; 03 to verified v24 source/hash. Do not rewind application data or broaden privileges.
